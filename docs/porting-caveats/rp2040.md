# RP2040 Porting Caveats

These notes describe the limitations and safety assumptions of the Oxide SE
`raspi-pico1` port, targeting the RP2040 Cortex-M0+ on a Raspberry Pi Pico.
They complement the [New Board Porting Guide](../newboard.porting.guide.md);
they are not a second porting procedure or a claim of production security.
Pending work remains tracked in [TODO.md](../TODO.md).

The CPU limitations below apply to RP2040. Flash capacity, boot2 selection,
UART wiring and the recorded hardware results apply to the tested Pico board,
not automatically to every board built around this microcontroller.

## Non-Cryptographic Random Source

**WARNING: the physical ROSC source is not cryptographically secure. Do not
use this development backend as a production source for keys, nonces or
secure-channel freshness.**

The driver reads the ROSC `RANDOMBIT` register at `0x4006001C` and assembles
eight samples per output byte directly in the caller's buffer. The CPU runs
from XOSC, independently of the oscillator being sampled. Running the CPU
from ROSC would correlate register sampling with the source itself.

The RP2040 datasheet, section 2.17.5, explicitly states that this source does
not meet security-system randomness requirements and can be compromised.
The driver performs no entropy conditioning or health certification. Its
bounded readiness check detects an unavailable oscillator, not a biased,
predictable or manipulated source. Eight samples are not a guarantee of
eight independent bits of entropy.

QEMU emulates the same register using guest entropy, or a reproducible stream
when `rosc-random-seed` is supplied. Emulated entropy quality says nothing
about physical ROSC quality. Passing `kernel_crypto --bench fill_random`
only validates the driver and APDU path.

Implementation: [raspi_pico.rs](../../kernel/core/src/core/target/raspi_pico.rs),
`crypto_initialize()` and `crypto_fill_random()`.
Reference: [RP2040 datasheet](https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf),
section 2.17.5.

## MPU-Based Stack Overflow Detection

RP2040 has neither `PSPLIM` nor `MSPLIM`. Oxide SE therefore relies on MPU
access permissions and memory placement rather than a hardware check of
every stack-pointer adjustment.

The Rustlet stack grows downward from its allocated RAM window. An access
below that window must be denied by the effective MPU mapping. The kernel
stack starts at the bottom of RAM and has a no-access guard immediately
below it. These arrangements depend on the linker layout and MPU region
priorities remaining consistent.

**A forbidden memory access triggers the protection; merely moving SP past
a boundary does not.** A guard region is not equivalent to a stack-limit
register. Large stack-pointer jumps, subsequent accesses, and exception entry
must be considered when reviewing a layout or fault-recovery change.

Do not interpret the no-op `app_stack_overflow_protection()` and
`kernel_stack_overflow_protection()` hooks as an absence of MPU protection:
these hooks correspond to stack-limit registers unavailable on ARMv6-M.

Implementation: [armv6m_profile.rs](../../kernel/core/src/core/target/armv6m_profile.rs),
the stack-guard setup and application MPU mapping;
[Pico1 linker script](../../kernel/native/raspi-pico/link.ld).

## HardFault Recovery Limitations

ARMv6-M has no separate MemManage or UsageFault exception. MPU violations
and invalid-instruction faults reach the HardFault path.

Oxide SE routes faults originating in Rustlet execution through its isolation
layer when an application call is active and the exception context allows
that path to run. Kernel-originated faults remain fatal. Recovery is not a
promise that every possible stack corruption, exception-entry failure or
nested fault can be contained.

Do not expect the detailed fault classification available on Cortex-M3/M4/M33.
The ARMv6-M adapter reports software fault status and available stacked PC/LR;
its common diagnostic structure uses zero for HFSR/CFSR and `None` for
MMFAR/BFAR. These values are placeholders, not evidence that hardware reported
no fault. Stacked registers are meaningful only when the saved frame is valid.

A Rustlet fault test must verify both the error response and subsequent kernel
liveness. A timeout or a terminated emulator is not successful isolation.

Implementation: [armv6m_profile.rs](../../kernel/core/src/core/target/armv6m_profile.rs),
the HardFault entry/dispatch and `last_mem_manage_fault()` paths.

## Flash Programming Requires RAM-Resident Code

The external flash is also the kernel's execute-in-place (XIP) storage.
Erase/program operations temporarily disable XIP. Between `flash_exit_xip()`
and restoration of XIP, all executed instructions and accessed data must be
available from SRAM, ROM or the relevant peripherals, not from XIP flash.
This includes callees, compiler-generated helpers, literal pools and program
input buffers.

The Pico1 erase/program routines reside in `.critical.kernel.fct`, copied
from flash into SRAM by native startup. They also require `#[inline(never)]`:
**a section attribute alone does not prevent the compiler from inlining a
routine into a flash-resident caller.** After changing this code or build
optimization, inspect the generated ELF and validate real flash operations.

The executable critical RAM area must remain outside the kernel's mutable-RAM
NX coverage. Do not solve an execution fault by making the heap executable.

The current port runs the kernel on core 0. Introducing timers, new interrupt
handlers, DMA flash reads or second-core execution requires an explicit audit
of the XIP-disabled interval. No interrupt vector fetch, handler or other
concurrent bus master may depend on flash while it is unavailable; moving only
the top-level erase/write function to RAM is not sufficient.

Implementation: [raspi_pico.rs](../../kernel/core/src/core/target/raspi_pico.rs),
`flash_erase_persistence_sector()` and `flash_write_persistence_page()`;
[native_rt0.s](../../kernel/native/raspi-pico/native_rt0.s),
`copy_critical_kernel_fct`.

## Flash Writes Are Not Power-Fail Atomic

This port programs 256-byte pages and erases 4096-byte sectors. Programming
changes bits from 1 to 0; returning bits to 1 requires erasing the whole sector.
A power loss may interrupt either operation. Read-back verification detects
some failures but does not make the physical operation atomic.

In particular, the `flash_write_page_atomic()` API name does not imply a
hardware power-fail guarantee on RP2040. Transaction safety belongs to the
persistent registry: write new objects first, then publish a CRC-valid registry
snapshot, while preserving the last committed snapshot and its referenced
objects until the new snapshot is committed.

Recycling must not erase a sector containing any still-required object or
snapshot, including an object being replaced by an uncommitted mutation.
An object may span several programming pages, but erasure still operates on
entire sectors. Never replace this policy with an in-place erase/rewrite of
the only committed data.

Implementation: [object_registry_persistence.rs](../../kernel/firmware/src/object_registry_persistence.rs).
For the persistence model and failure assumptions, see chapter 6 of the
[manual](../manual/Chapter_6.tex).

## Board-Specific Boot and Flash Assumptions

The `raspi-pico1` layout declares 2 MiB of external flash. The native image
includes a fixed, checksummed 256-byte boot2 for W25Q080-compatible flash.
It configures XIP and transfers control through the vector table at
`0x10000100`; it does not encode a Rust function address that must be patched
after each build.

For another RP2040 board, check its flash chip, supported commands, capacity
and boot2 compatibility. Update the board layout and persistence reservation
together. A successful QEMU boot does not prove that the physical boot ROM and
flash chip will accept the same image.

The APDU link uses UART0 on GPIO0 (TX) and GPIO1 (RX), at 115200 baud, 8N1.
The debug probe's USB serial bridge is separate from SWD: connect target TX
to probe RX, target RX to probe TX, and a common ground. Open the host serial
link before releasing reset to avoid losing the ATR.

Use `--trace=none` for standalone execution. Debug traces must be explicitly
enabled and serviced by the debugger; an unconditional semihosting breakpoint
in startup can prevent boot without debugger support.

Implementation: [boot2_w25q080.S](../../kernel/native/raspi-pico/boot2_w25q080.S),
[raspi_pico.rs](../../kernel/core/src/core/target/raspi_pico.rs), and the
[OpenOCD runner](../../xtask/src/testing/openocd.rs).

## Validation Scope

The following narrow hardware checks passed on the connected Pico1 during
the 2026-08-31 bring-up, with native ELF and `--trace=none`:

| Scenario | Observed result |
| --- | --- |
| `kernel_ping` | 34 checks, including direct and GET RESPONSE payloads up to 255 bytes |
| `kernel_t0` | 4 transport checks |
| `kernel_flash` | 5 checks over three boots, retaining writes across resets without reflashing |
| `kernel_registry` | 75 checks over three boots, including persistent object replacement |
| `kernel_crypto` | 3 checks: random output, AES-128 CBC and P-256 key generation |
| `kernel_crypto --bench <operation>` | 9 checks: `fill_random`, `aes_cbc`, `aes_ecb`, `aes_iso9797_m2`, `cmac`, `hkdf`, `x963`, `p256_generate_keypair`, `p256_ecdh` |

The complete hardware run passed 130 checks across 14 scenario invocations.
The dedicated `fill_random 32` check also passed during initial ROSC bring-up.
The default P-256 benchmarks took approximately 6.015 seconds for key generation
and 6.134 seconds for ECDH, measured as host APDU round-trip times rather than
isolated algorithm execution times.

Each hardware scenario's generated `kernel.elf` was inspected with
`arm-none-eabi-objdump -d`: no semihosting `BKPT 0xAB` instruction was found.
Temporary crypto entry/exit probes have been removed. Configurable panic/fault
diagnostics remain available for deliberate debug builds.

The same physical board subsequently passed these scenarios with
`--on openocd --trace=none --allow-destructive`:

| Scenario | Checks | Scope |
| --- | --- | --- |
| `gp_noscp` | 5 | Null SD discovery and rejection of SCP establishment |
| `gp_scp03 --scp03=all` | 104 | Full S8/S16 scenarios, including Rustlet installation/execution and child SD policy |
| `gp_scp11a` | 19 | Full scenario, including protected installation and subsequent Rustlet execution |
| `gp_scp11b` | 19 | Full scenario, including management restrictions and subsequent Rustlet execution |
| `gp_scp11c` | 45 | Full scenario, including malformed inputs, replay, management policy and Rustlet execution |
| `rustlet minimal_valid_test` | 6 | Installation, selection and application APDU cases |
| `rustlet_all` | 102 | Aggregate application, serialization, allocator, fault-recovery and termination campaign |
| `rustlet_isolation` | 17 | Read/write violations, invalid instruction, panic and post-fault liveness |
| `rustlet ecdh_test` | 5 | P-256, HKDF-SHA256 and fresh SCP11c session material |
| `rustlet stack_overflow_recursive_test` | 4 | Recursive overflow recovery and subsequent liveness |
| `rustlet complete_security_domain` | 3 | Security Domain ABI, installation and selection |
| `gp_rustlet_security_domain_scp03` | 39 | SCP03 S8/S16/33, key rotation, protected management and application execution |

Before the full SCP scenarios, the `--without-rustlets` variants passed
separately: 78 checks for SCP03 S8/S16, 14 for SCP11a, 15 for SCP11b, and 40
for SCP11c. These narrower runs are not substitutes for the full scenarios.
All results above are functional development results subject to the ROSC
security warning; they do not upgrade the entropy source's assurance.
The delegated SCP03 and SCP11a/b/c Rustlet SD campaigns were not completed on
hardware in this run because repeated persistent-state writes made the full
sequences impractically slow. They remain available as explicit runner
commands; this is a performance limitation to investigate, not evidence that
those scenarios pass.

Run these scenarios from the repository root with an explicit board and
backend, for example:

```sh
cargo run test kernel_ping raspi-pico1 --on openocd --trace=none --allow-destructive
cargo run test kernel_crypto raspi-pico1 --on openocd --trace=none --allow-destructive --bench fill_random 32
```

**These commands erase firmware and persistent registry contents on the
connected board.** Use disposable contents and select the serial/probe
explicitly if several devices are connected; consult `cargo run test <test>
--help` for the options.

QEMU has separate validation evidence. The ROSC read also passed under QEMU,
as did both `kernel_stack_guard` and `kernel_ram_nx`. Those two fault scenarios
deliberately use semihosting diagnostics in their dedicated `core_test.elf`;
this is not a dependency of the trace-free hardware kernel image.

Emulated peripheral behavior is not a substitute for physical validation.
The checks above do not establish full hardware Rustlet isolation, exhaustive
crypto coverage, all GP campaigns, power-cut tolerance or production security.
The OpenOCD `kernel_stack_guard` and `kernel_ram_nx` observation paths are
currently restricted to Pico2; their availability there is not validation of
Pico1 on hardware.

The runner accepts single-Rustlet scenarios, `rustlet_all`,
`rustlet_isolation`, `gp_security_domain`, `gp_predeployment` and
`gp_rustlet_security_domain_*` on Pico1 through the same APDU scenarios as QEMU.
This does not promote the board's catalogue support level. The extended
OpenOCD campaigns `gp_registry`, `gp_persistence`, `gp_all` and
`gp_scp11a_install_load` remain restricted to Pico2.
